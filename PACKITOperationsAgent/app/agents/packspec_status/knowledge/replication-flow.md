---
concept: replication-flow
summary: How a payload travels source to target: PDMI, Solace, TOPICSTRING, Message Type, Transfer, Replication Status.
loads_when: always
---

**Source System**:
The SAP S/4 system (current instance: PD7) where PACKIT runs and where a Packaging Specification and its Determination Record are created and approved.

**PDMI**:
The middleware layer that an approved Determination Record's Packspec Payload passes through en route to Target Systems. Comprises Customer Adapters, Solace, MongoDB, and Talend.

**Packspec Payload**:
The JSON representation of an approved Packaging Specification (with its Determination Record) that the Source System publishes into PDMI once the Determination Record's Workflow Status is Accepted.

**Solace**:
The pub/sub message broker within PDMI that pushes a Packspec Payload out to Subscriber Target Systems. Maintains one FIFO queue per Message Type, confirmed by the PDMI team. Aside from a generic reliability caveat with no specific diagnostic signature, messages aren't expected to get stuck in Solace itself — a stuck-looking Transfer is a Target System question, not a Solace one.

**TOPICSTRING**:
The Solace subscription topic string (technical field: `TOPICSTRING`), confirmed real and confirmed to be the actual routing mechanism — not just descriptive metadata. Generated by the Source System at publish time as part of the payload and passed to Solace, which uses it to determine which Subscribers receive the message. Its business-context segments (Sales Channel, Determination Type, Plant, Packspec Status, for `PackITPackagingSpecification`) differ by Message Type — see `components/transform` for the confirmed segment-by-segment shape per type. Confirmed full PS shape: `ESR/Native/{MessageType}/{SourceSystem}/V1/{SalesChannel}/{DetType}/{Plant}/{PackspecStatus}/{MassChange}`, where three of those segments are literally `OBJECTKEY` fields (`DETTYPE`, `WERKS`) or body fields (`PACK_USAGE`, `HEADER.STATUS`) — identical on all 266 PS records in the corpus.
**The trailing segment is `No` for a normal change and `Yes` for a mass change** — confirmed by the domain owner 2026-08-07. Constant `No` across every capture here, so a `Yes` has never been observed and a mass change would look different from anything this project has seen.
**TOPICSTRING appears at two levels and they are not the same string.** `SINGLEMESSAGEHEADER.TOPICSTRING` and its sibling `SINGLEMESSAGES[n].TOPICSTRING`. For a PS both carry the business context; for a `DocumentInfoRecord` the header-level copy is coarse (`Native/DocumentInfoRecord/SAPPD70110` — Message Type and Source System only) while only the sibling carries Document Type. Reading "the" TOPICSTRING without saying which level therefore gives different answers per Message Type. The header-level copy never includes a Target System; the body-level copy per hop does, appended at the end — this is the direct mechanism behind a single Message ID fanning out to multiple Transfers (see Transfer).

**Subscriber**:
A Target System (R/3 or S/4) registered to receive Packspec Payloads via Solace.

**Message Type**:
Identifies which kind of object a Transfer's Packspec Payload carries: `PackITPackagingSpecification` (the PS itself), `DocumentInfoRecord` (a Dependent Object), or `PackITPackagingCockpitMasterData` (a Dependent Object). Each is published and tracked as its own separate Transfer, even when they originate from the same PS. Confirmed real: Splunk indexes this as each event's own `source` field (a real, reliable, filterable field — not something that has to be found via full-text search) — though a real minority of events carry a `Native/`-prefixed variant (e.g. `Native/PackITPackagingSpecification`) rather than the bare name, so a filter on this field needs a leading wildcard to catch both. See `components/splunk-client`.

**Replication Status**:
Whether an approved Determination Record's Packspec Payload has successfully reached and validated in its Target System(s), as opposed to still being in transit, or having failed target-side validation. The second of two stages an end user's "status" question can be about, downstream of Workflow Status — a spec can be Accepted (Workflow Status) yet still failing or pending on Replication Status. Applies uniformly across all Determination Types (SHIP, RCPT, ZFER, STOC, PALE, DOLL) — the pipeline doesn't differentiate by transaction purpose. Visible today via a Splunk dashboard. One of: successfully COMPLETED, Technical Error, Business Error, RETRY, or no status in raw data. A PS's true Replication Status isn't just its own Transfer's outcome — it also depends on its Dependent Objects' Transfers, since the Target System won't process the PS until those are done.

**Transfer**:
One Message ID's full processing history for a Packspec Payload moving from Source System to **one** Target System — one or more hops (an Initial Trigger, then zero or more Retriggers), each carrying its own Replication Status and Status Description. Properly identified by (Message ID, Target System), not Message ID alone: confirmed live (multiple real examples) that a single Message ID can fan out to *several* Transfers, one per Target System it reaches, each with its own independent hop history and independent outcome — e.g. resolved on one Target System while still failing on another, at the same point in time. What Splunk's search grid lists one aggregated row per (latest hop wins) — per Transfer, i.e. per Target System, not per Message ID; the Expert View shows every hop of one Transfer.

**Expert View**:
**It deduplicates, so its row count is not the hop count — confirmed by the domain owner 2026-08-07.** The Expert View collapses repeated identical hops, so a Transfer showing 4 rows can have 11 hops underneath: PS `00000000040000348796` (`splunkExamples/example10`) displays 4 lines while carrying 3 SOLACE hops, a publish hop, **six** identical Business Errors and a final Success.
_Consequence_: never reconcile our hop count against the dashboard's row count and treat a difference as a bug in either — they are counting different things, and ours is the raw one. Equally, never quote a dashboard row count as the number of attempts; six daily failures collapse to one row and the six-day history disappears with them.
