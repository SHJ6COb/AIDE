loads_when: has_multiple_hops
---

**Host**:
A field on each raw hop of a Transfer (in Splunk) indicating which processing attempt produced it — not simply "the Target System." `CPI_{Source System}_{Target System}_CONSUMING` (e.g. `CPI_SAPPD70110_SAPP870110_CONSUMING`) marks the Initial Trigger. `{Target System}_CONSUMING` — the same, minus the `CPI_{Source System}_` prefix — marks a Retrigger. A bare `CPI_{Source System}_{Target System}` (no `_CONSUMING` suffix) marks that same target's pre-consumption *publish*-stage hop, timestamped a few hundred ms before its own `_CONSUMING` hop — previously documented only as a `PackITPackagingCockpitMasterData`-specific variant, now confirmed general: it appears identically for `PackITPackagingSpecification` targets too (including a PT0/VITAA target), it just went unnoticed there because it only causes a visible problem on a multi-target fan-out (see the Fixed defect note below), and Cockpit Master Data always has exactly one target. `SOLACE` marks the message-broker delivery hop itself, not a Target System processing attempt at all — genuinely shared/untargeted, unlike the bare `CPI_..._{Target System}` shape above. Target System must be derived by stripping both the optional `CPI_{Source System}_` prefix and the `_CONSUMING` suffix — the exact pattern is Message-Type-dependent, confirmed to differ between `PackITPackagingSpecification` and `PackITPackagingCockpitMasterData`.
_Fixed defect (2026-08-05)_: `transform.py`'s `_derive_target_system` only recognized the `_CONSUMING`-suffixed host shapes as target-specific, despite the bare `CPI_{Source}_{Target}` shape already being documented — so it was still misclassified as shared/untargeted in code. Harmless for single-target records (Cockpit Master Data), but on a real multi-target `PackITPackagingSpecification` fan-out, one target's own publish hop could sort chronologically after a *different* target's genuine terminal hop and silently become that other target's latest hop, reporting a false no-status result. Caught via live cross-check against `screenshots/results/00000000040001498023_*.png`; see `docs/components/transform/TECHNICAL_SPEC.md`.
_Exception_: `DocumentInfoRecord`'s Host values (confirmed live: `STCENEMXX0_PUBLISHING`, `STCENPSXX0_PUBLISHING`) are content/document-server names with a `_PUBLISHING` suffix, not `{Target System}_CONSUMING` — the Target System derivation rule above does not apply to it at all. Note: the "PS" in `STCENPSXX0` is confirmed unrelated/coincidental — not an abbreviation for Packaging Specification.

**Initial Trigger**:
A Transfer's first processing attempt, delivered directly via Solace. Identified by a `CPI_`-prefixed Host.

**Reprocessing cadence**:
How often the Target System re-attempts a failed Transfer — and it is **not** one rate.
**Once per day, for a Business Error — confirmed by the domain owner 2026-08-07.** The target runs a scheduled reprocessing job that picks up business-error Transfers once daily. Confirmed against `splunkExamples/example10` (PS `00000000040000348796` at `SAPP870110`): the Initial Trigger failed at 14:39 on 29 Jul, then retriggers ran at **01:00, 01:05, 01:00, 01:03, 01:01 and 01:03** on the six following days — spaced 23.91h to 24.09h apart, all in the same five-minute slot after midnight — failing identically each time until the underlying master data was fixed and the seventh attempt succeeded.
_Why it matters operationally_: the gap between attempts **is** the diagnosis. Six attempts spread over six days is a Transfer nobody has touched in a week, and the next attempt is tomorrow morning — not something that will resolve on its own in minutes. Reporting "6 attempts" without the cadence loses that entirely.
**Frequently, for a Technical Error — confirmed by the domain owner 2026-08-07.** `splunkExamples/example5` (PS `00000000040001253724`) retriggered **100 times in about 8 hours** at the same target, alternating roughly 2.5 and 7.5 minutes apart. Its error, `SNR13 not found/ Mark for deletion`, is a *technical* error, and technical errors are retried on a fast loop rather than the daily job.

**What tells them apart — and it is not the error text or the catalog.** The two cases are indistinguishable on target, Message Type, Message ID count, and `d:BusinessStatus` (both simply `ERROR`). Both even match the catalog as `Target Error` (rows 2 and 14), so **`error_category` in `error_catalog.yaml` is a different axis from the dashboard's Business/Technical split and must not be read as one**. The one structural difference is the SAP message code in the `Ret_msgs` feed:

| capture | code | error | cadence |
|---|---|---|---|
| `example5` | `/RB9X/PD4P_EAI/**109**` | SNR13 not found / Mark for deletion | technical → minutes |
| `example10` | `/RB9X/PD4P_EAI/**009**` | Packaging material doesn't exist in plant | business → daily |

Same message class, different number. `Hop.message_codes` now carries it (it was parsed and discarded until 2026-08-07, leaving free error text as the only thing anything could classify on).
_Still unconfirmed_: whether the number alone determines the class, and how it maps across the other 61 catalog rows. Two data points establish that the code is *the field to look at*, not what the mapping is. Until that mapping exists, **do not tell a user which cadence applies to their Transfer** — state the observed gaps between attempts, which are always true.

**Retrigger**:
A subsequent processing attempt **at the Target System** after a Transfer failed on its Initial Trigger (or a prior Retrigger). At regular intervals the Target reprocesses failed Transfers by Message ID, calling the PDMI Adapter to re-pull the payload from Solace. Identified by a Host *without* the `CPI_` prefix, and **reuses the original Message ID** — a Transfer with many Retriggers is one trigger the Target keeps failing to process. Confirmed real example: a Transfer whose Initial Trigger and first Retrigger both failed with the same Business Error (an invalid packaging material), and whose second Retrigger succeeded — presumably once the underlying master data was corrected. Real scale seen live: PS 00000000040001253724 has 100 Retriggers of a single Message ID over ~8 hours.
_Avoid_: retry (this project's own vocabulary, matching the Docupedia catalog's "Retrigger required" category, is "Retrigger" — "RETRY" is Splunk's own dashboard status-bucket label for this same concept, spelled differently but referring to the same thing). **Also avoid using this word for a Re-publish** — that is the Source System re-sending, a different operation with a different fix (see Re-publish).

**Re-publish**:
The **Source System** sending a PS again with no change made to it — one new Initial Trigger per Determination Record, each by its own `SEQNO`. Distinguished from a Retrigger by three things: a **new Message ID each time** (Message ID is per trigger, per Message Type), a `CPI_`-prefixed Host, and one hop per trigger rather than many hops under one. The Activation Counter is unchanged, since nothing about the PS structure changed. Confirmed real at scale: PS 00000000040001497551 shows 48 Re-publishes to `SAPPOE0110` in ~24 hours, all at Activation Counter `2`, all `CPI_`-prefixed.
**Why the distinction matters operationally**: many Retriggers means the message arrived and the Target cannot process it — the fix is at the Target (the SNR13, the material, the plant status). Many Re-publishes means the Source keeps re-sending — the fix is wherever the source-side blocker is. Describing both as "attempts" hides which of the two is happening.
_Avoid_: retry (this project's own vocabulary, matching the Docupedia catalog's "Retrigger required" category, is "Retrigger" — "RETRY" is Splunk's own dashboard status-bucket label for this same concept, spelled differently but referring to the same thing)
