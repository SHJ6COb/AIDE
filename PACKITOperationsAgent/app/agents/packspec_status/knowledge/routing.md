**Additional Routing**:
The routing-plan configuration that Solace/PDMI consults to decide which Target System(s) actually receive a given Transfer — separate from, and in addition to, TOPICSTRING/Solace's own subscription mechanism. Confirmed real and important: a PS being Active and successfully triggered does **not** guarantee it reaches any one specific expected destination — the actual destination(s) are determined by this Plant + Determination Type + Sales Channel-keyed routing plan (queried live via the `ROUTINGPLAN` API, see `components/routing-plan`), which can legitimately route the same criteria to more than one destination at once (confirmed real, intentional dual-delivery, not a misconfiguration) or to a destination other than the one a user expects (e.g. PT0 instead of/alongside a normal Target System, for IAM/OES). This is the mechanism-level explanation for why the same Message ID can fan out to multiple Transfers (see Transfer) — each routing-plan entry names exactly one Target System, so fan-out happens via multiple separate entries sharing the same criteria, not one entry with several targets.
Confirmed real: this plan is keyed **generically** by Plant + Determination Type (+ occasionally Sales Channel), **never** by an individual PS, its Change Number, or its Determination Record — an entry's own PS/Change-Number/Sequence-Number/Material/Supplier criteria are always unscoped across the entire plan, with no exception found. So "why didn't PS X reach system Y" is never answerable by looking up PS X itself in this plan — it's answered by first reading PS X's own Plant and Determination Type off its Transfer, then asking what the plan says for *that* Plant/Determination Type combination. Sales Channel scoping (e.g. PT0's IAM/OES) is carried inside the entry's own TOPICSTRING text, not as an independently-queryable criterion sitting alongside Plant/Determination Type.
_Avoid_: Assuming Replication Status failures/gaps are always explained by the Transfer's own hop history — a PS that never even shows up at an expected Target System may be a routing-plan question, not a Splunk/Transfer question at all. Also avoid assuming "unscoped by Plant" and "scoped to apply to every Plant" are the same thing — the plan does contain a handful of entries genuinely authored to apply universally across Plants (a real, deliberate config choice, confirmed rare: 4 of 554 `PackITPackagingSpecification` entries), which is a distinct case from simply not filtering a query by Plant at all.

**PT0**:
The **aftermarket approval system**, and the owner system for sellable SNR13 products (technical host: `SAPPT00110`), confirmed real. For IAM/OES Sales Channel PSs, the intended flow is: PT0 approval first (while Packspec Status is 35/37, an intermediate/pre-Active state) → PD7 packaging approval → Packspec Status set to 60 (Active) → normal replication to the PS's actual Target System(s). Uses a distinct message class (`/RB0T/FIT_PACKIT`) from the normal Target System replication path (`/RB9X/PD4P_EAI`), confirming it's a genuinely separate processing step, not just another Target System in the usual sense. The specific trigger that sends a PS to PT0 is confirmed real and named **VITAA**.
**The approval-skip rule — confirmed 2026-08-06.** IAM/OES *always* goes for VITAA/PT0 approval, with one exception: a customization table in PD7 can maintain an approval-skip rule **keyed by plant**, and a PS at such a plant is never pushed to VITAA. So a missing PT0 step is not automatically a fault — it is a second legitimate reason (alongside Additional Routing) that an expected system never sees a Transfer, and it cannot be diagnosed from Splunk at all, only from that customization table. Confirmed at scale via the Additional Routing plan (554 entries): PT0 is **exclusively** SHIP + IAM/OES — zero exceptions — and **not** related to the `KIT` Determination Type despite both being narrow/special-purpose cases; `KIT` routes normally alongside SHIP/RCPT/ZFER to the regular Target Systems.
_Avoid_: Treating a PT0-targeted Transfer the same as a normal Target System replication — it's a pre-Active approval step specific to IAM/OES, not the PS's eventual destination.
