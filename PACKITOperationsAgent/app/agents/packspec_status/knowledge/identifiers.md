**SNR10 / SNR13**:
The product/material number a Determination Record resolves a PS for. **SNR10** is the bare 10-digit product number (technical: `MATNR`). **SNR13** is that number plus the Packaging Index (technical: `MATNR_SNR13` = `MATNR` + `PACKINDEX`) — confirmed across every capture in this repo, e.g. `0281009441` + `04Y` = `028100944104Y`. **When `PACKINDEX` is empty the value is simply the 10-digit SNR10** (real example: `F00C2G8057`), which is exactly why the error catalog's rows 2 and 3 say "the 10- **or** 13-digit number" rather than naming one length. Nothing may assume a 13-character value.
**This is the number most target-side errors are actually about**, so an answer that says "the SNR13" without naming it is not actionable — an engineer pastes `028100944104Y` into the target system, not the phrase.
_Avoid_: Conflating the PS's own SNR10/SNR13 with a **packaging material** number named inside an error description. They are different things and often different values: PS 00000000040000434427's own SNR13 is `0273011047211` while its error reads "T141 Bom item status Invalid for material 6000.409.798" — a packaging material, at a plant (`078W`) the PS itself never references. Cross-attributing the two sends someone to fix the wrong material at the wrong plant.

**Sales Channel**:
A field on the Determination Record whose **real values are `OE`, `OES` and `IAM` — three separate values**, confirmed 2026-08-06 across every capture in the repo. `IAM/OES` is prose for the combined aftermarket channel PT0 serves (see PT0); it is not a value any payload carries, and code that expected it matched nothing.
**The technical field is `PACK_USAGE` — and this is a genuine naming trap, confirmed 2026-08-06.** SAP named the *Sales Channel* field `PACK_USAGE`, while the entirely unrelated *Usage* concept (Regular / Alternative 1–4) lives in `ABRVW`. So Splunk's dashboard label "Pack Usage" is not a mislabel at all — it is faithfully showing the field's real technical name; an earlier version of this entry wrongly called it a Splunk error. The collision is SAP's, and it is why the two business terms must be kept strictly apart in any answer.
_Not_ `LABEL_SALESCHANL`, despite the name, and despite an earlier version of this entry treating the two as the same field. `LABEL_SALESCHANL` is empty on every inbound (RCPT) record while `PACK_USAGE` is populated on all 254 PS records in the repo and agrees with the TOPICSTRING Sales Channel segment (`…/V1/OES/SHIP/0110/60/No`) every single time, inbound included. On outbound the two happen to hold the same value, which is exactly why reading the wrong one went unnoticed. What `LABEL_SALESCHANL` actually means — presumably the channel governing label data, which has no meaning on a goods receipt — is not yet confirmed.
_Avoid_: "Pack Usage" as a *business* term (it is the technical field name of Sales Channel, and saying it invites confusion with Usage). Reading `LABEL_SALESCHANL` for this value.

**Message ID**:
The identifier (technical field: `MESSAGEID`, equal to `Uuid` on the same record) generated by the Source System (PD7) at publish time for a Packspec Payload. Stable for that payload's entire processing lifecycle — a Retrigger reuses the original Message ID rather than minting a new one, confirmed against real Splunk data (the same `MESSAGEID` recurring across two hops of the same PS, minutes apart, same Target System). A Re-publish, by contrast, mints a new one.
**Message ID identifies a trigger, not a business object, and it is per trigger *per Message Type*.** A PS and its Dependent Objects therefore never share a Message ID, so it can never be used to link them — see Dependent Object for what does. The business object is identified by `OBJECTKEY` (PS ID + `SEQNO` + Activation Counter + the Determination Record's own dimensions).
Not, by itself, a unique identifier for a Transfer either — see Transfer.
