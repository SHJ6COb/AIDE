# transform — Technical Specification

Modules: `app/tools/splunk_xml_parser.py` (pure XML parsing, no domain knowledge) + `app/tools/transform.py` (domain-aware). Exposed internally to the `get_ps_status` pipeline (see [`docs/agents/packspec-status/TECHNICAL_SPEC.md`](../../agents/packspec-status/TECHNICAL_SPEC.md); these are no longer separate LLM-facing tools, see [ADR-0001](../../adr/0001-single-deterministic-pipeline-tool.md)). Both modules are implemented and validated — see the fixed-bugs section below for what an extensive parallel-agent validation pass against real dashboard screenshots found and corrected.

## Fixed bug: a Message ID is not always a 1:1 key for a Transfer

`group_transfers` originally grouped hops purely by Message ID, on the assumption (matching `CONTEXT.md`'s original **Transfer** wording) that one Message ID maps to one Target System. **Confirmed live, three independent real examples**, that a single Message ID can legitimately fan out to more than one Target System, each with its own independent hop chain and independent outcome — e.g. a PS resolved (Success) on one target while still failing (Business Error) on another, at the same point in time. Grouping by Message ID alone silently collapsed these into one `TransferRecord`, whose `.current_status` picked whichever target's hop happened to sort chronologically last — masking a real, unresolved error on the other target. Reproduced deterministically (both from real partial data and a full synthetic pairing) before fixing.

**Fix**: `group_transfers` now groups by `(message_id, target_system)`. Hops with no determinable target (`SOLACE`, or any pre-consumption hop for a Message Type with no Target System concept at all, e.g. `DocumentInfoRecord`) are attached to every target-specific group sharing that Message ID, since they're shared context regardless of how many targets the message eventually reaches. `TransferRecord` gained an explicit `target_system` field. For every case with only one real target (the large majority), this produces exactly the same single `TransferRecord` as before — re-validated against the full corpus of real data gathered during this investigation with zero regressions on any single-target case.

## Fixed bug: `parse_hop()` was not exception-safe on its own

`group_transfers` always caught parsing failures, but `parse_hop()` — a public, documented function meant to be usable standalone (e.g. for single-record inspection) — did not: truncated/malformed `Payload` JSON, an empty `SINGLEMESSAGES` array, or a non-dict `OBJECTKEY` all raised raw `json.JSONDecodeError`/`KeyError`/`IndexError` instead of the documented `UnrecognizedPayloadShape`. Confirmed via direct fuzz testing (not from any real captured record — the real data happened not to exercise this path). **Fixed**: the risky sections of both `_parse_atom_hop` and `_parse_plain_json_hop` now catch those exceptions and re-raise as `UnrecognizedPayloadShape`, so `parse_hop()` has exactly one documented failure mode regardless of caller.

## Fixed bug: bare `CPI_{Source}_{Target}` publish hosts were misclassified as untargeted

`_derive_target_system` only matched the `_CONSUMING`-suffixed host shapes, even though fact 2 below already documented the bare `CPI_{Source}_{Target}` (no suffix) pre-consumption host shape. That meant such a hop always returned `None` from `_derive_target_system` and, per `group_transfers`'s rule for untargeted hops, got attached to *every* target-specific group sharing that Message ID. This was invisible for `PackITPackagingCockpitMasterData` (always exactly one target, `SAPPOE0110`) — an untargeted hop shared across "every" group is harmless when there's only one group. It broke silently on a real multi-target `PackITPackagingSpecification` fan-out (PS `00000000040001498023`, targets `SAPP990110` + `SAPPOE0110` from one Message ID): `SAPP990110`'s own status/description-less publish hop (timestamped *after* `SAPPOE0110`'s genuine terminal Atom hop, but *before* its own) sorted last within `SAPPOE0110`'s group by the time cross-checked, ended up as a NEW, separate group's `.latest` instead — reporting `status=None, description=None` for `SAPP990110` despite the dashboard showing it as Success with `"...ECM Already exist"`. Caught via live cross-check against `screenshots/results/00000000040001498023_*.png`, not from a synthetic case. **Fixed**: `_derive_target_system` now also matches the bare `CPI_{Source}_{Target}` shape via a second regex, falling back to it only when the `_CONSUMING` pattern doesn't match. Regression test: `tests/test_transform.py` (fixture captured from the real live search that exposed this).

## Confirmed grounding facts (live Splunk data, cross-checked against the dashboard)

1. **Raw XML shape**: Splunk export XML (`<results><result><field k="...">...`). Each `<field k="_raw">` wraps its content in `<v>` — note this differs structurally from every other field, which uses `<value><text>`. Splunk also splits `_raw` text with `<sg>` highlight tags around matched search terms; extraction must use `''.join(v.itertext())`, not `v.text`, or the value silently truncates at the first highlighted term.

2. **Envelope shape is determined by hop stage, not by Message Type.** This corrects the earlier (wrong) assumption that envelope shape is a Message-Type property:
   - **Pre-consumption hops** (`host=SOLACE`, and any pre-`_CONSUMING`/pre-`_PUBLISHING` publish-side host, e.g. `CPI_SAPPD70110_SAPPOE0110` with no `_CONSUMING` suffix) are **plain JSON**, straight from the Source System's publish event: `{"SINGLEMESSAGES":[{"SINGLEMESSAGEHEADER":{SOURCESYSTEMID, MESSAGEID, MESSAGETYPE, OBJECTKEY, ...}, "SINGLEMESSAGEBODY": {...}}]}`. `DocumentInfoRecord` additionally wraps this in an outer `{"COLLECTIVEMESSAGE": {MESSAGEID, TIMESTAMP}, "SINGLEMESSAGES": [...]}`.
   - **The actual Target-processing hop** (`{Target}_CONSUMING`, `CPI_{Source}_{Target}_CONSUMING`, or DIR's `STCENxxx_PUBLISHING`) is **Atom/OData XML** — this is the Target SAP Gateway's own response format, confirmed identical in shape across all three Message Types at this stage: `<entry><content><m:properties><d:Uuid>...</d:Uuid><d:Payload>{JSON string}</d:Payload>[<d:BusinessStatus>ERROR|SUCCESS</d:BusinessStatus>]</m:properties></content></entry>`.
   - **Parsing gotcha**: a nested `Ret_msgs` feed (see below) is inline-expanded via `<link rel=".../Ret_msgs"><m:inline><feed><entry>...`, and this `<link>` appears in the XML *before* `<content>` in standard Atom ordering. A naive `entry.find('.//m:properties')` (document-order, first match) grabs a nested `ReturnMsg`'s properties instead of the outer entry's own — always select via the explicit path `entry/content/m:properties` (or the namespaced equivalent), never a bare `.//` search.
   - **Field vocabulary also changes across this same boundary, independent of the wrapper.** Pre-consumption JSON uses SAP-native ALL-CAPS fields (`OBJECTKEY`, `DOCUMENTNUMBER`, `SINGLEMESSAGEBODY`). The Atom-wrapped `Payload` JSON for `PackITPackagingSpecification`/`PackITPackagingCockpitMasterData` still uses this same ALL-CAPS `SINGLEMESSAGES`/`OBJECTKEY` shape — but for `DocumentInfoRecord` at its Atom-wrapped (`STCENxxx_PUBLISHING`) stage, the `Payload` JSON uses a **different, camelCase vocabulary**: `{"DocumentMessageRoot": {changeNumber, dataRecordResponsibleDepartment, documentNumber, documentPart, documentType, ...}}` — confirmed real, but with no properties observed yet that indicate a per-hop status (see gap below).

3. **The real PS-linkage field for a `DocumentInfoRecord`** (correcting an earlier wrong guess) is `SINGLEMESSAGEBODY.OBJECTLINKSPACKITPACKSPEC` — an array, confirmed shape: `[{"PS_ID": "...", "PNCNT": "...", "ZZACTCOUNTER": N, "WERKS": "...", "SUPPLIER": "...", "PACKINDEX": "...", "PDS_RELEVANCE": "..."}]`. This is only present at the pre-consumption (plain JSON) stage — the Atom-wrapped/`DocumentMessageRoot` stage's linkage field, if any, is unconfirmed (see gap below). Also confirmed: this array can be `null` — a DIR with no PS link at all is a legitimate, unrelated document, not an error.
   - _Previously documented (wrong) path_: `SINGLEMESSAGEBODY.DocumentMessageRoot.hasPackItPackagingSpecificationLink[0].{hasPackagingSpecification, hasPlant, hasSupplier}` — this field path does not exist in real data. Discard it.

4. **`d:BusinessStatus`** (`"ERROR"`/`"SUCCESS"`) plus a nested `Ret_msgs` feed of `ReturnMsg` entries (`Type` `''`/`'S'`/`'E'`, `Id` + `Number` as a stable structured message code, human-readable `Message`) drive status + description, for `PackITPackagingSpecification` and `PackITPackagingCockpitMasterData`. Description = newline-joined non-empty `Message` values — confirmed byte-for-byte against a real dashboard screenshot (PS `00000000040000829552`: `"SNR13 not found/ Mark for deletion"`), not just a captured screenshot in isolation.
   - **`DocumentInfoRecord` gap**: its Atom-wrapped payload has been observed with **no `d:BusinessStatus` property at all** (only `Uuid` and `Payload`). Both real examples found were presumably-successful publishes. How DIR signals an error at this stage — a different property name, or absence from this host/stage entirely on failure — is genuinely unconfirmed, not just undocumented.

5. **Grouping**: aggregate by Message ID — `latest(_time)` row supplies status/description/detail fields, `earliest(_time)` shown separately. **Message ID is confirmed stable across an entire retry chain** (generated once at Source System publish time; a Retrigger reuses it rather than minting a new one) — validated live: the same `MESSAGEID`/`Uuid` recurring across two hops of the same PS, ~86 seconds apart, same host, same error. See `CONTEXT.md`'s **Message ID** entry.

6. **Target System derivation**: strip a `_CONSUMING` suffix from `host` (optionally also a `CPI_{Source}_` prefix) — confirmed for `PackITPackagingSpecification` and `PackITPackagingCockpitMasterData` (the latter always targets `SAPPOE0110`, confirmed). **This rule does not apply to `DocumentInfoRecord`** — its hosts (`STCENEMXX0_PUBLISHING`, `STCENPSXX0_PUBLISHING`) are content/document-server names, not Target System IDs, and use a `_PUBLISHING` suffix instead of `_CONSUMING`. `SOLACE` is the broker-delivery hop for all types — never a Target System, exclude it from derivation entirely.

7. **Multi-hop Transfers**: one Message ID can carry several hops over time — confirmed real example: Solace-delivery → Initial Trigger (Business Error) → Retrigger (same Business Error, ~86s later) → eventual Retrigger (Success). `group_latest_per_message` still returns the *latest* hop's status as the Transfer's current Replication Status (unchanged rule) — but `TransferRecord` should retain the full ordered hop list too, so the pipeline can explain the *history* ("failed twice, then succeeded after a retrigger") rather than only the current snapshot. Per the token-minimization principle ([`ARCHITECTURE.md`](../../ARCHITECTURE.md)), the full hop list is computed internally regardless but only serialized into the LLM-facing result when a fixed code rule decides it's warranted (e.g. hop count is small) — never based on an LLM-set flag.
   - Real retry cadence observed: hops for a persistently-failing PS are spread minutes-to-tens-of-minutes apart, not densely packed — a narrow time window (e.g. the default 15 minutes) can legitimately miss earlier hops of an active retry chain that's still ongoing.

8. **`TOPICSTRING`'s confirmed segment structure** (see `CONTEXT.md`'s **TOPICSTRING** entry for what it *is* — this is the confirmed *shape*, per Message Type, from ~115+ real distinct examples). Segments are `/`-delimited; the header-level copy (`SINGLEMESSAGEHEADER.TOPICSTRING`) never includes a Target System, the body-level copy (`SINGLEMESSAGES[0].TOPICSTRING`) appends it at the end:
   - `PackITPackagingSpecification`: `ESR/Native/PackITPackagingSpecification/{SourceSystem}/V1/{SalesChannel}/{DetType}/{Plant}/{PackspecStatus}/{Yes|No}[/​{TargetSystem}]`. `{PackspecStatus}` confirmed real values: `60` (Active), `35`/`37` (PT0-only intermediate, see `CONTEXT.md`'s **PT0** entry), `DL` (deletion indicator) — see **Packspec Status** in `CONTEXT.md`. The trailing `Yes`/`No` segment is confirmed: `Yes` = the trigger was carried from the Source System via a mass create/change/extend operation (a batch update), `No` = a normal (individual) trigger.
   - `PackITPackagingCockpitMasterData`: `ESR/Native/PackITPackagingCockpitMasterData/{SourceSystem}/{Brand}/{PackIndex}` (e.g. `MOT/B7L`, `_/000` when Brand is blank) — a completely different shape from PS, no Sales Channel/DetType/Plant segments at all. Both segments confirmed by exact field match against the same record's `OBJECTKEY`: `{Brand}` = `OBJECTKEY.BRAND` (e.g. `"MOT"`), `{PackIndex}` = the suffix of `OBJECTKEY.SNR13_MATERIAL` remaining after removing the `SNR10_MATERIAL` prefix (e.g. `SNR13_MATERIAL="0265025049B7L"` minus `SNR10_MATERIAL="0265025049"` = `B7L`) — i.e. the same Packaging Index / Customer Index concept used elsewhere (see `CONTEXT.md`'s **Customer Index**).
   - `DocumentInfoRecord`: `DocumentInfoRecord/V1/REGULAR/{SourceSystem}/{DocumentType}/{DataRecordResp}/{OrgOfficeId}/{Laboratory}` (e.g. `.../BV/3000/50399481/K91`) — confirmed by exact field match against the same record's `SINGLEMESSAGEBODY.MAINDATA`: `DATARECORDRESP="3000"`, `ORGOFFICEID="50399481"`, `LABORATORY="K91"`, all standard SAP DMS (Document Management System) fields, not PACKIT-specific. Segments can be `_` when blank (e.g. `.../PAC/_/_/_`).
   - Not currently used for parsing/derivation (Target System is derived from `host`, not from this trailing segment) — recorded here as confirmed domain grounding, not yet load-bearing in `transform.py`.

9. **`PackITPackagingSpecification`'s own content structure** (`SINGLEMESSAGEBODY.DETERMINATION`, confirmed real) — recorded here as confirmed domain grounding; `packspec-status` doesn't need any of this today (it only reads `SINGLEMESSAGEHEADER.OBJECTKEY`, `BusinessStatus`, and `Ret_msgs`), but a future capability that needs to explain PS *content* (not just Replication Status) would start here rather than re-deriving it:
   - `DETERMINATION` = the Determination Record's own fields (`PS_ID`, `VALID_FROM`/`VALID_TO`, `MATNR_SNR13`, `PACK_USAGE`, `DOCUMENT_LINKS`, ...) plus a nested `HEADER` = the PS header itself.
   - `HEADER`: `PS_ID`, `STATUS` (the PS's own Packspec Status, a **letter** code — `A` Active, `N` New, `DL` deletion indicator). **Not the same concept as TOPICSTRING's numeric status segment** — corrected 2026-08-08. That numeric code is the *Determination Record's* Workflow Status (`60` Accepted, `35`/`37` VitAA waits), on a different object; the two correlate because a PS goes Active when its Determination Record is Accepted, which is why they were previously recorded as one field. See `knowledge/packaging-specification.md`. Also `PS_GROUP`, `LEVEL_SET`, `ZACTCOUNTER` (single Z here — see `knowledge/activation-counter.md` for why this differs from DIR's `ZZACTCOUNTER`), `CONTENTS` (array of Content nodes), `LEVELS` (array of Level nodes).
   - `HEADER.CONTENTS[]` (Content node): `MATNR`/`MAKTX` (the product and its description), and `SUB_PS_ID`/`SUB_PS_GUID` — confirmed real as the PSTV-integration mechanism, see `CONTEXT.md`'s **Content node** and **PSTV** entries.
   - `HEADER.LEVELS[]` (Level node): `LEVEL_SEQ`, `LT_DESCRIPTION` (human-readable, e.g. `"Level 1"`), `HU_MAT_TEXT` (the packaging material's own description), full weight/volume/dimension fields, `LEVEL_ELEMENTS` (array of Element nodes).
   - `LEVELS[].LEVEL_ELEMENTS[]` (Element node): `ELEMENT_TYPE` (confirmed real values `VERP`, `VHIB` — distinct categories, meaning not yet further confirmed), `ZIDENTIFIER` (confirmed real: value `P` marks the Level's one Main Packaging Material, `U` otherwise), `ZKIT` (confirmed real: marks an Element as inherited from an integrated PSTV — unrelated to the `KIT` Determination Type despite the name), `ZPACKMATNR` (the packaging material number — matches the Docupedia catalog's `60xxxxxxxx` material references), `ZOWNERSHIP`, `OUTER_LENGTH`/`OUTER_WIDTH`/`OUTER_HEIGHT`.

## Status derivation — grounded in the Docupedia catalog's category mapping

Not guesswork: the dashboard's 5 status buckets map onto the Docupedia catalog's own Error Category column (confirmed with the domain owner):

| Dashboard bucket | Catalog Error Category | Notes |
|---|---|---|
| successfully COMPLETED | (n/a — `BusinessStatus == SUCCESS`) | |
| Business Error | Target Error + Source Error | doc's own intro groups these as "Business errors" |
| Technical Error | Technical Error | per catalog row 29: does **not** auto-retry, unlike everything else |
| RETRY | Retrigger required | |
| no status in raw data | (fallback — nothing matched) | safe default, never silently reclassified as an error |

Catalog HINT / No action required rows aren't failure states at all (e.g. "valid from date not reached" — nothing's wrong, just wait).

**Confirmed live at production scale**: Technical Error category rows (30-32, "Error while saving the Det rule... Do not enter packing instructions twice" and variants) matched **91/91** real examples once `match_catalog` used `DOTALL` (see [`components/catalog`](../catalog/TECHNICAL_SPEC.md)). By contrast, the Business-Error-bucket SNR13 family of rows failed on **167/168** real examples in the same investigation, for an unrelated reason (missing literal scaffolding text) — see the catalog spec for the full breakdown. RETRY-bucket (`Retrigger required`) examples were searched for over both a 24-hour and a targeted 7-day window and not found — those two catalog rows (6, 7) are narrow edge cases (specific plants 8150/8160) that may simply not have fired recently; treat as still-unconfirmed rather than assume the shape is wrong.

## Dependent Object blocking

Confirmed by Docupedia catalog rows 57/58 ("Cockpit master data dependent object still in progress" / "DIR dependent object still in progress") — these are Source Error messages that appear **on the PS's own transfer record**, not something requiring a separate search to discover the fact of blocking. The pipeline's dependent-object lookup is therefore only called when a PS's own status/description matches this pattern, to find out *which* dependent is stuck and why — not on every PS lookup. The linkage mechanism itself (PS_ID via `OBJECTLINKSPACKITPACKSPEC` for DIR, `OBJECTKEY.PS_ID` directly for Cockpit-MD) is confirmed correct.

**Partially validated live (2026-08-05)**: ran the lookup end-to-end against a real blocked PS (`00000000040000908526`, row 57 / Cockpit-blocked) over a 30-day window — it genuinely found **zero** `DocumentInfoRecord`/`PackITPackagingCockpitMasterData` Transfers for that PS ID at all, not a lookup bug (confirmed by a broad, unscoped full-text search on the same PS ID over the same window: every one of the 46 real results was the PS's own `PackITPackagingSpecification` Transfer). Most likely explanation, consistent with row 57's own solution text ("check TC Z0MP_BUS_ERR_LOG... on PD7"): when the blocking dependent object is itself stuck at the **Source** system before ever being published into PDMI, it never becomes a Splunk-visible Transfer at all — there's nothing to cross-reference in that case, and the catalog row's own guidance (check the Source system directly) is the correct fallback, not a further Splunk search. Still open: a real example where the dependent object *does* show up as its own Transfer, to confirm the cross-reference path when one exists.

## Error handling

Any payload shape that doesn't match a known pattern raises a typed `UnrecognizedPayloadShape` error rather than guessing or silently dropping fields.

## Confidence status (honest, updated after extended live Splunk investigation)

- **HIGH, confirmed at scale**: `PackITPackagingSpecification` Business Error path (envelope, `Ret_msgs`/description derivation, Message ID stability, Target System derivation) — validated against hundreds of real examples across a 15-minute, 4-hour, and 3-hour pull, and cross-checked byte-for-byte against a real dashboard screenshot.
- **HIGH, confirmed at scale**: Technical Error category matching (rows 30-32) — 91/91 real examples matched once `DOTALL` is used.
- **RESOLVED**: envelope shape is a function of hop stage (pre-consumption = plain JSON, Target-processed = Atom/OData), not of Message Type — this applies uniformly across all three Message Types, superseding the earlier "two envelope shapes by Message Type" framing entirely.
- **RESOLVED**: `PackITPackagingCockpitMasterData` always targets `SAPPOE0110`; its pre-consumption host omits the `_CONSUMING` suffix (`CPI_{source}_{target}`) as a third, previously-undocumented host variant alongside the full `_CONSUMING` form and `SOLACE`.
- **RESOLVED**: `DocumentInfoRecord`'s real PS-linkage field path and its non-`_CONSUMING`, content-server-style host naming (see facts 2, 3, 6 above).
- **STILL UNCONFIRMED**:
  - How `DocumentInfoRecord` signals error vs. success at its Atom-wrapped (`STCENxxx_PUBLISHING`) stage — no `d:BusinessStatus` property was observed on either real example found, both presumably successful. `DocumentMessageRoot`'s `status` field (e.g. `"10"`) is **confirmed by the domain owner to be an unrelated SAP document lifecycle status, not a replication success/failure signal** — ruled out as a candidate, don't re-investigate it.
  - RETRY-bucket (`Retrigger required`) payload shape, for any Message Type — actively searched for (24h + 7-day targeted hunts) and not found; likely genuinely rare rather than a shape we have wrong.
  - The "latest hop wins" grouping rule at scale — confirmed on 2-hop cases, not verified against the larger (~50-100 hop) retry chains observed to exist.
  - End-to-end cross-referencing of a blocked PS against its actual stuck dependent-object record in one dataset (both confirmed independently, not yet paired).
