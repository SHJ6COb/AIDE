# splunk-client — Technical Specification

Module: `app/tools/splunk_client.py`. Exposed as the `splunk_search` tool.

## Confirmed live, via the real Bosch gateway (Phase 0 — no longer an assumption)

The user live-tested the full call chain in Postman against the real instance. This is ground truth, not documentation-derived guesswork:

- **Base URL is a Bosch API gateway**, not a raw Splunk `host:8089`: `https://ews-esz-emea.api.bosch.com/pdmi/splunk` (internally backed by `rb-itoa-splunk-pdbb.de.bosch.com:8089`, per the job-status response's `<id>` field — matches the `_si`/`splunk_server` values already seen in every real payload example, e.g. `rb-itoa-splunk-i2-pdbb`).
- **Auth is a custom header, not Bearer/Basic**: `KeyID: {SPLUNK_API_TOKEN}`. Confirmed via Postman ("Auth inherited from Collection: No Auth" — the actual auth is a plain request header named `KeyID`, not anything in Postman's Auth tab).
- **The real call flow is async/normal mode (4 calls), not oneshot**:
  1. `POST /services/search/jobs` — form body `earliest_time`, `latest_time`, `search` (e.g. `| search index=pdbb PackITPackagingCockpitMasterData 00000000040000588527`) → `201 Created`, body `<response><sid>{sid}</sid></response>`.
  2. `GET /services/search/jobs/{sid}` — poll until `<s:key name="dispatchState">DONE</s:key>` (also carries `resultCount`/`eventCount`).
  3. `GET /services/search/v2/jobs/{sid}/results` (note: `v2` here, unlike steps 1/2) — returns the actual `<results><result>...` XML, confirmed to exactly match the shape already reverse-engineered from every prior example (`_bkt`, `_cd`, `_indextime`, `_raw`, `host`, `index`, `source`, `sourcetype`, `splunk_server`, `_time`, etc.).
  4. `DELETE /services/search/jobs/{sid}` — cleanup, frees the job server-side (`200 OK`, `"Search job cancelled."`).
- **Search syntax confirmed**: full-text term search against `_raw`, no field-extraction filtering used (e.g. `search index=pdbb PackITPackagingCockpitMasterData 00000000040000588527` — Message Type name and PS ID both as bare search terms) — validates the full-text default assumed earlier.
- **New correction from this live data**: `PackITPackagingCockpitMasterData` results confirmed to come through the same export wrapper as the PS message type — but its `host` field follows a *different* naming convention: `CPI_{source}_{target}[_CONSUMING]` (e.g. `CPI_SAPPD70110_SAPPOE0110_CONSUMING`), not just `{target}_CONSUMING`. The Target System derivation rule (`transform.py`) must be Message-Type-aware, not a single universal suffix-strip rule.

## Design

Build around the confirmed 4-call flow above — not oneshot. `output_mode=xml` throughout, matching every example captured so far. Auth: send `KeyID: {SPLUNK_API_TOKEN}` as a plain header on every call. Step 4 (DELETE) should run in a `finally` block so a job is always cleaned up even if parsing the results fails.

```python
def build_spl(params: SearchParams, index: str, sourcetype: str) -> str: ...
def search(config: AgentConfig, params: SearchParams) -> str:  # returns raw XML text
```

`build_spl` constructs something like:
```
search index=pdbb sourcetype=Native source="*PackITPackagingSpecification" "<PS_ID>"
| head 200
```
Message Type is filtered via `source=` **with a leading wildcard** (a real, confirmed indexed field, but not always the bare Message Type string — see the field-mapping experimentation below for why the wildcard is mandatory, not stylistic), everything else (PS_ID, Message ID, any other value living inside the JSON payload) via bare, quoted full-text terms — confirmed live that no field extraction exists for anything inside `_raw`'s JSON body, so those values have no `field=value` alternative.

## SPL construction guardrails ("strong guardrails" requirement)

Interpolating LLM-derived and user-derived text into a server-built search string is a real injection surface (SPL supports pipes and commands, similar in spirit to SQL injection):

1. **Tier 1 fields** (see `docs/agents/packspec-status/TECHNICAL_SPEC.md`): validated against enums/patterns *before* string building — an invalid value never reaches the SPL string, it's rejected upstream.
2. **Tier 2 free-text terms** (`additional_terms`): each checked against a strict allowlist (alphanumeric, spaces, `.`, `-`, `_` only) and a length cap. Any term containing a pipe (`|`), backtick, or other SPL-special character is **rejected outright**, not escaped.
3. **All interpolated values** (Tier 1 or Tier 2) are wrapped in double quotes in the final SPL, not left bare — removes ambiguity about where a term ends, even though the one live-confirmed real example used bare terms.
4. **The base search structure is a fixed template** the code controls (`search index={index} sourcetype={sourcetype} source="*{message_type}" {quoted terms...} | head {cap}`) — no part of the *structure* is ever built from LLM/user-derived text, only the *values* plugged into validated slots. `message_type` is itself a Tier 1 (enum-validated) value, just placed in the `source=` field-filter slot (with the code-controlled leading wildcard, never LLM-controlled) rather than as a bare term (see the field-mapping experimentation below for why both the field and the wildcard are required).
5. **Result cap** (`| head 200`) is always code-appended, never LLM-overridable — mirrors the dashboard's own 50,000-result warning.

`build_spl` is a pure function, fully unit-testable without network access, including negative tests asserting a Tier-2 term containing `|` is rejected before it ever reaches the SPL string.

Cap results (`| head 200`) to avoid an unscoped search blowing up, mirroring the dashboard's own 50,000-result warning banner.

## The result cap is not optional — confirmed by a real gateway block, not just the dashboard's warning banner

Live-tested directly: requesting an unbounded result set (`count=0` on the results endpoint) against a broad, unscoped search (`search index=pdbb`, no message-type/PS filtering) that matched 46,844 events in a 15-minute window was **hard-rejected by the API gateway** with a SOAP `env:Fault` / `fault:MessageBlocked` response — not a Splunk-level error, a gateway-level block before the payload is even built. The same block recurred at `count=800` against a smaller (~5,300-match) but still-broad search. `count=200` succeeded reliably in every test; fetching more than 200 rows requires paginating via the `offset` parameter across multiple calls (confirmed working: `offset=0`, `200`, `400`, `600`, ... each as a separate `results` call against the same `sid`), not requesting a larger single page. Treat 200 as the practical safe per-call ceiling, not just a stylistic choice mirroring the dashboard.

A secondary, unrelated practical note from the same testing: a `results` call fetching a full 200-row page of `PackITPackagingSpecification`/`DocumentInfoRecord` data (rich, deeply-nested payloads) can legitimately take 100-200+ seconds to complete — this is normal for this sourcetype's payload size, not a sign of failure. `SPLUNK_SEARCH_TIMEOUT_SECONDS` (currently `60` in `.env`) is too short for a full 200-row fetch and will need raising, or the harness should expect to paginate in smaller chunks (e.g. 50 rows per call) if a shorter timeout must be kept.

## Confirmed via direct `search=` field-mapping experimentation (13 live variant calls, same chain-of-thought as `components/routing-plan`'s `Request-Filter` investigation — see `docs/RESEARCH_PLAYBOOK.md`)

This resolves the previously-"still open" question ("whether Splunk has field extractions for this sourcetype at all") with a definitive, evidence-backed answer, and corrects the SPL-construction design above in one important way.

- **`source` is a real, reliable, indexed field — confirmed to hold the exact Message Type string on every event**, for all three Message Types (`PackITPackagingSpecification`, `PackITPackagingCockpitMasterData`, `DocumentInfoRecord`), cross-checked directly against captured raw XML (`r.get('source')`) before ever querying live. `search index=pdbb source="PackITPackagingSpecification"` is a genuine field filter, not a text-search fallback — confirmed live at both large (24h window) and small (fixed window) scale.
- **No field extraction exists for anything inside the JSON payload itself.** `search index=pdbb PS_ID="<a real, currently-live PS_ID>"` returned **zero** results, against a fixed window where the equivalent bare-text term search for the same PS_ID is independently confirmed (below) to have 16 real hits. This is a clean, definitive negative result, not just an untested assumption anymore: **`field=value` syntax only works for Splunk's own default/indexed fields (`source`, `sourcetype`, `host`, `index`, `_time`, ...), never for a key living inside `_raw`'s JSON body** (`PS_ID`, `MESSAGEID`, `SOURCESYSTEMID`, `OBJECTKEY.*`, etc.) — those remain reachable only via bare/quoted full-text term search against `_raw`, exactly as `build_spl` already does.
- **`source=` filtering is case-insensitive** (`source="packitpackagingspecification"` lowercase returned the identical count to the real-cased value, on an identical fixed window) and **supports wildcards** (`source="PackIT*"` returned a *larger* count than the exact match, cleanly explained by `PackITPackagingCockpitMasterData` sharing the same `PackIT`-prefix and being included too — not a bug, a real confirmed prefix collision between two of the three real Message Type names).
- **An unrecognized `source` value returns a clean, empty result** (`resultCount: 0`) — no error, no non-JSON sentinel. This is a useful contrast with the `ROUTINGPLAN` API's `AR AGREEMENT NOT REGISTERED` plain-text-body surprise (`components/routing-plan`): different backend, different failure-mode contract for the same *shape* of question ("this value doesn't exist") — a reminder from the playbook not to assume error-handling conventions carry over between systems just because both are internal Bosch APIs.
- **`sourcetype=Native` is currently redundant, not required** — omitting it entirely from the SPL (`search index=pdbb source="..."`, no `sourcetype` clause at all) returned the exact same count as including it, on an identical fixed window. Every real event seen across every investigation this session has `sourcetype=Native`; nothing has surfaced a second sourcetype under `index=pdbb`. Keep it in `build_spl` anyway as defensive, self-documenting scoping (cheap, and protects against a future second sourcetype silently entering the mix) — but it is not currently load-bearing.
- **Combining a `source=` field filter with a bare-text term is the confirmed-best pattern for scoping.** `search index=pdbb sourcetype=Native source="PackITPackagingSpecification" "<PS_ID>"` returned exactly the same 16 hits as PS_ID alone (the PS_ID string didn't happen to collide with another Message Type in this case) — but doing so costs nothing and removes the (real, if currently unobserved) risk of a bare PS_ID/Message-ID string coincidentally appearing inside an unrelated Message Type's payload. **Recommend updating `build_spl`'s template to filter Message Type via `source="{message_type}"` (a real field) rather than as a bare quoted term** — strictly more precise, same guardrail treatment (it's still an interpolated, validated Tier-1 value, just placed in a different slot of the fixed template).
- **RESOLVED — the small discrepancy between bare-text-term and exact `source=` matching has a confirmed root cause.** On the same fixed epoch window, exact `source="PackITPackagingSpecification"` returned 20,589 against the bare-text term's 20,605 — a 16-event gap. Cause found: **`source` isn't always the bare Message Type string** — a real, already-known minority of events (confirmed: 35 across every sample gathered this session, out of ~1,320 `PackITPackagingSpecification` events) carry a `Native/PackITPackagingSpecification` prefix instead (this is exactly why `transform.py`'s `_strip_message_type` already exists and strips it before use — a fact this investigation initially overlooked despite it already being implemented). A **leading-wildcard** field filter, `source="*PackITPackagingSpecification"`, closes the gap exactly: re-run on the identical fixed window, it returned **20,605** — matching the bare-text count precisely. **`build_spl` must use a leading wildcard on `source`, not an exact match**, or it will silently under-count by missing every `Native/`-prefixed event.
- **Methodology note, generalizable beyond this investigation**: the first (rolling-window) comparison above produced a misleading result purely from timing — two calls a few seconds apart against `-15m`-to-`now` sample different underlying event sets, since the window's own boundaries move between calls. **Any live A/B comparison between two search formulations must pin both calls to the same fixed, absolute `earliest_time`/`latest_time`** (explicit epoch seconds, as used here, or an equivalent fixed timestamp), never two independent relative-time calls — otherwise an apparent "finding" may just be measuring elapsed wall-clock time. Added to `docs/RESEARCH_PLAYBOOK.md` as a refinement to its "cross-validate" step.
- **`NOT` exclusion against a bare-text term works as expected** — `source="PackITPackagingSpecification" NOT "SUCCESS"` returned 20,560 against the same fixed window's 20,589 total (29 events containing the literal string `SUCCESS` somewhere in `_raw`, consistent with a `d:BusinessStatus` of `SUCCESS`). Confirms `NOT` is safe to use in the SPL template for a future "show me only the failures" framing, without needing a dedicated field.

## Confirmed live: `status` as a search filter — bare-word unreliable, exact structural tag precise

Adding `SearchParams.status` (validated `ReplicationStatus` enum, `ERROR`/`SUCCESS`) surfaced a real, previously-unmeasured precision problem, live-tested on a real 3-hour window (`-3h` to `now`):

- **Bare-word `"ERROR"`**: 200/200 real matches had `BusinessStatus=ERROR` — 0 false positives. Clean.
- **Bare-word `"SUCCESS"`**: 200/200 matches, but only **4** had `BusinessStatus=SUCCESS` — the other **196** were pre-consumption (`plain_json`) hops with no status at all (`business_status=None`, `description=""`). The literal word "SUCCESS" apparently occurs incidentally elsewhere in a pre-consumption payload's raw text far more often than it occurs as a real completed-transfer signal. This is a different, sharper measurement than the earlier `NOT "SUCCESS"` exclusion test above (29/20,589 ≈ 0.14% of *all* events contain the string at all) — that test measured overall rarity, not precision of an inclusion filter; the two aren't in tension, but the inclusion case turned out to be far noisier than the rarity figure alone would suggest.
- **Exact structural tag `"<d:BusinessStatus>SUCCESS</d:BusinessStatus>"`**: 200/200 real matches, all genuinely `BusinessStatus=SUCCESS` — 0 false positives. This is the fix: search for the literal Atom/OData tag (see `components/transform`'s confirmed envelope shape), not the bare word.

**`build_spl` implements the exact-tag form as a code-controlled clause** (`params.status.value` is always one of the two enum strings, never LLM/user-derived free text) — it is deliberately *not* routed through Tier 2's free-text guardrail, since that guardrail's character allowlist would reject the `<`/`>` characters the tag requires anyway. Same treatment as `message_type`'s `source="*{value}"` clause: a Tier-1, enum-validated value placed into a fixed, non-bare-term slot of the template.

The `count=0`/large-`count` gateway-block behavior and the resulting pagination requirement are new, confirmed-necessary design constraints, not present in the original design.

**RESOLVED**: the small count discrepancy between bare-text-term and `source=` field matching — root-caused to the real `Native/`-prefixed `source` variant (already known to `transform.py`, previously not connected to this investigation) and fixed by requiring a leading wildcard in `build_spl`'s `source=` slot (see above); re-verified exact on a fixed window (20,605 = 20,605).
