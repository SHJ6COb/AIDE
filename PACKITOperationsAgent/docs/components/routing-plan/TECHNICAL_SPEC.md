# routing-plan — Technical Specification

A separate API/data source from Splunk — exposes the Additional Routing configuration that Solace/PDMI consults to decide which Target System(s) actually receive a Transfer. See `CONTEXT.md`'s **Additional Routing** entry for what this is and why it matters (a PS being Active and successfully triggered doesn't guarantee arrival at any one specific expected destination — this config is the other half of the answer, alongside TOPICSTRING/Solace subscription).

## Confirmed live (real API calls against the Bosch gateway)

- **Endpoint**: `GET https://ews-esz-emea.api.bosch.com/services/P/ROUTINGPLAN` (config: `ADDITIONAL_ROUTING_URL`).
- **Auth**: `KeyId` header (config: `ADDITIONAL_ROUTING_API_TOKEN`) — a different token from the Splunk `KeyID` header, despite the similar mechanism.
- **Filtering**: not query params — a `Request-Filter` header carrying a JSON object, e.g.:
  ```
  Request-Filter: {"SINGLEMESSAGEHEADER":{"SOURCESYSTEMID":"*","MESSAGETYPE":"PackITPackagingSpecification","LOGICALCONNECTION":"*"}}
  ```
  `*` is a real, working wildcard (confirmed: `SOURCESYSTEMID:"*"` returned all 554 `PackITPackagingSpecification` entries in the plan).
- **Response shape**: a JSON array, each entry `{"SINGLEMESSAGEHEADER": {SOURCESYSTEMID, MESSAGETYPE, LOGICALCONNECTION, OBJECTKEY: {...same shape as Splunk's OBJECTKEY, values may be "*"...}, TOPICSTRING, TARGETSYSTEMS: [{"SYSTEMID": "..."}]}}`.
- **Field-naming gotcha, confirmed real**: `SOURCESYSTEMID` in this API does **not** mean the literal originating Source System (always `SAPPD70110`/PD7 in this domain) — it identifies the **Target/Subscriber system whose routing plan you're querying**, and always matches that entry's own `TARGETSYSTEMS[0].SYSTEMID`. Confirmed by filtering on a specific value (`SAPP1M0110`) and getting back 74 entries where both fields were `SAPP1M0110` throughout. The real originating system appears instead as `OBJECTKEY.SYSTEMID` (`SAPPD70110`).
- **Each entry has exactly one Target System** — across the full 554-entry plan (unscoped, `SOURCESYSTEMID:"*"`), zero entries have more than one `TARGETSYSTEMS` value. Fan-out to multiple Target Systems (see `CONTEXT.md`'s **Transfer**) is implemented as *multiple separate routing-plan entries* sharing the same (Plant, Determination Type, Sales Channel) criteria but pointing at different targets — not as one entry listing several targets.

## Confirmed patterns (from the full 554-entry plan, `MESSAGETYPE=PackITPackagingSpecification`)

- **10 distinct Target Systems** appear as routing-plan destinations, `SAPPT00110` (PT0) the single largest by entry count (136/554).
- **PT0 is exclusively `SHIP` + `IAM`/`OES` Sales Channel** — 136/136 of its entries, 0 exceptions. Confirmed **not** related to `KIT`, despite `KIT` also being a narrow/special-purpose Determination Type (PSTU) — `KIT` routes normally alongside `SHIP`/`RCPT`/`ZFER` to the 7 "regular" targets, never to PT0.
- **7 "regular" targets** (`SAPP790110`, `SAPP810110`, `SAPP990110`, `SAPP720110`, `SAPP870110`, `SAPP740110`, `SAPP450110`) each handle `SHIP`/`RCPT`/`ZFER`/`KIT` uniformly per Plant (equal entry counts across all 4 Determination Types per target), Sales Channel `*` (unscoped) throughout.
- **`SAPP1M0110` concentrates `STOC`/`PALE`/`DOLL`** (the three repacking Determination Types) almost exclusively, plus a smaller slice of `SHIP`/`RCPT`/`KIT` scoped to Sales Channel `OE` specifically — a materially different pattern from the 7 regular targets. Not yet confirmed with the domain owner whether this reflects a formally distinct role (e.g. a dedicated repacking-operations system) or is incidental.
- **Intentional dual-delivery, confirmed real**: 3 (Plant, `SHIP`, Sales Channel `*`) combinations map to two different targets simultaneously — Plant `8150` and `9050` → both `SAPP450110` and `SAPP1M0110`; Plant `3000` → both `SAPP1M0110` and `SAPP790110`. Confirmed by the domain owner to be intentional, not a misconfiguration — both targets are genuinely supposed to receive these.
- Sales Channel scoping (PT0's IAM/OES, a portion of `SAPP1M0110`'s OE) is carried in each entry's own `TOPICSTRING` text, not in a queryable `OBJECTKEY` field — see the correction below; `OBJECTKEY.ABRVW` itself is `*` on all 554 entries with no exceptions.

## Confirmed via direct Request-Filter experimentation (13 live variant calls, `MESSAGETYPE` held fixed)

This section is about *how a user's question maps to a `Request-Filter` at runtime* — the mechanics of the filter object itself, not the routing data's business patterns (previous section).

- **`OBJECTKEY` sub-fields are genuinely server-side filterable**, not just descriptive of the response. Nesting `"OBJECTKEY":{"WERKS":"8150"}` inside `SINGLEMESSAGEHEADER` returned exactly the 10 entries the full unscoped dump independently shows for that Plant; `{"DETTYPE":"KIT"}` returned exactly 92, matching the full dump. Combining both (`WERKS=8150` + `DETTYPE=SHIP`) returned exactly the 2-entry dual-delivery case (`SAPP450110` + `SAPP1M0110`) directly — confirming a single filtered call, not client-side post-filtering, is enough to answer "which target(s) does Plant 8150's SHIP flow go to."
- **Critical asymmetry — `"*"` does NOT mean the same thing at every nesting level.** At the top level (`SOURCESYSTEMID`, `LOGICALCONNECTION`), `"*"` is a true match-all wildcard (this is how the 554-entry full dump was obtained). But inside `OBJECTKEY`, `"*"` is treated as a **literal exact-match string**, not a wildcard — `{"OBJECTKEY":{"WERKS":"*"}}` returned only **4** entries (confirmed against the full dump: exactly 4 real entries — all `SAPPT00110`/`SHIP` — genuinely have the literal string `"*"` stored as their own `WERKS` value), not all 554. **The correct way to leave an `OBJECTKEY` sub-field unscoped is to omit the key entirely from the filter object, never to pass `"*"` for it.** This is the single easiest mistake a naive query-builder (LLM or code) would make, since `"*"` reads as "wildcard" everywhere else in this API.
- **`LOGICALCONNECTION` is a mandatory header field, `SOURCESYSTEMID` filtering is exact-match only.** Omitting `LOGICALCONNECTION` from the filter entirely returns **HTTP 400**: `{"errorClass":"java.lang.IllegalArgumentException","errorMessage":"LOGICALCONNECTION is missing or empty for MESSAGETYPE: PackITPackagingSpecification"}` — always send it, even as `"*"`. `SOURCESYSTEMID` supports only exact match or the bare `"*"` wildcard — partial/glob patterns (`"SAPP4*"`) are **not** supported; a partial pattern is treated as a literal (unregistered) exact value, see below.
- **An unregistered/unknown `SOURCESYSTEMID` does not return an empty JSON array — it returns HTTP 200 with a plain-text, non-JSON body: `AR AGREEMENT NOT REGISTERED`.** Confirmed reproducible with two different bogus values (`SAPBOGUS9999`, `ZZZNOTREAL`) and with the unsupported partial-wildcard case above. **A routing-plan client must check for this literal sentinel string before attempting to parse the response as JSON** — treating it as "this Target/Source system has no Additional Routing agreement at all" is the correct interpretation, not an error.
- **An unrecognized `OBJECTKEY` sub-field name** (made up, not in the real schema — e.g. `BOGUSFIELD`) is accepted (HTTP 200) but matches **zero** entries, rather than being ignored or raising an error — the API applies it as a real filter condition against a field that doesn't exist in any entry. Silent zero-result, not silent ignore: a typo'd field name in a runtime-built filter fails closed (empty result) rather than falling back to unscoped.
- **Case-sensitive, exact-match only.** `{"DETTYPE":"ship"}` (lowercase) matched **zero** entries against the real `"SHIP"` — no case-folding.
- **`OBJECTKEY.ABRVW` (Sales Channel) is never actually populated as a filterable value in the underlying data** — every one of the 554 entries stores `ABRVW: "*"` literally, including PT0's IAM/OES-scoped entries. Filtering `{"ABRVW":"IAM"}` returns 0 (consistent with the case-sensitive-exact-match rule above, since no entry's actual `ABRVW` is `"IAM"`). **Sales Channel scoping exists only inside the `TOPICSTRING` string** (e.g. `.../V1/IAM/*/*/*/No`), not as a live `OBJECTKEY` filter dimension — confirmed by direct inspection of the two `SAPPT00110`/IAM and /OES entries. This corrects the earlier framing ("Sales Channel `*` throughout... only PT0's IAM/OES-scoped entries... filter on it") — refine it to: PT0's Sales-Channel-scoping is baked into the pre-rendered `TOPICSTRING`, not into an `OBJECTKEY.ABRVW` filter value, since that field is uniformly `"*"` everywhere.
- **Routing is keyed generically (Plant × Determination Type × Sales Channel), never per individual PS.** Filtering `{"OBJECTKEY":{"PS_ID":"<a real, currently-active PS ID>"}}` returned **zero** entries — confirmed by cross-checking the full dump too: `PS_ID`, `AENNR`, `SEQNO`, `ZACTCOUNTER`, `MATNR`, `SUPPLIER` are `"*"` on all 554 entries, no exceptions. **Practical consequence for the future capability this spec supports**: answering "why didn't PS X reach system Y" can never filter the routing plan directly by that PS's own ID — it must first resolve the PS's own `WERKS`/`DETTYPE` (and, if ever populated, Sales Channel) from its own Transfer/Splunk data, then query the routing plan with *those* values.

## Confidence status

REST mechanics (endpoint, auth, `Request-Filter` header, wildcard support) confirmed live via 15+ real calls, including systematic filter-variant experimentation (see section above). The `SOURCESYSTEMID`-means-target-not-source field-naming gotcha, the zero-multi-target-per-entry fan-out mechanism, the omit-vs-`"*"` asymmetry for `OBJECTKEY` sub-fields, and the `AR AGREEMENT NOT REGISTERED` non-JSON sentinel are all confirmed from live data, not inferred. Still open: whether `LOGICALCONNECTION` ever takes a real non-`*` value in practice (always `*` in every one of the 554 real entries; confirmed mandatory as a filter key, but never seen populated); `SAPP1M0110`'s exact business role; whether this same API/mechanism applies identically to `DocumentInfoRecord`/`PackITPackagingCockpitMasterData` (only `PackITPackagingSpecification` has been queried so far).

**Wired in (2026-08-05)**: `app/tools/routing_plan.py` implements `query_target_systems(config, plant=..., determination_type=...)`, applying exactly the filter-building rules confirmed above (omit unscoped `OBJECTKEY` sub-fields rather than passing `"*"`, always send `LOGICALCONNECTION`, check the `AR AGREEMENT NOT REGISTERED` sentinel before parsing JSON). Called from `app/agents/packspec_status/pipeline.py`'s `_check_routing_if_target_missing` -- fires only when a search scoped to a specific `target_system` finds nothing there; broadens the search (drops `target_system`) to resolve the PS's real Plant/Determination Type from wherever it *is* found, then asks this API whether the originally-requested target was ever configured to receive that combination. Fails closed (`RoutingCheck` stays unset) on any ambiguity -- PS not found anywhere, unresolvable Plant/Determination Type, or the API call itself failing -- rather than guessing. See `harness.py`'s `_not_found_answer` for how the result is surfaced to the end user.
