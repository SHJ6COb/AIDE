# Single deterministic pipeline tool, not four LLM-orchestrated tools

`packspec-status` exposes one LLM-callable tool, `get_ps_status(params) -> StatusResult`, instead of four (`splunk_search`, `parse_and_transform`, `lookup_dependent_objects`, `match_catalog`). Those four remain internal, independently unit-testable Python functions — `get_ps_status` runs them as a fixed deterministic pipeline (search → transform → branch → catalog-match) with no LLM involvement in between, and returns one already-summarized, output-context-shaped result. The LLM's only two jobs per query are: (1) parse the question into `SearchParams`, and (2) compose `plain_language_answer` from that result.

We considered letting the LLM drive all four tools call-by-call (the harness's original "tool-calling loop" framing). Rejected because it risks the LLM skipping `match_catalog` or stating a Suggested Action before checking dependent objects — the strict grounding rule is only a guarantee if the code enforces the order, not the LLM's judgment — and because it costs 3 extra round trips (and their token overhead) for a sequence that has no real decision points once `SearchParams` is fixed. See [`ARCHITECTURE.md`](../ARCHITECTURE.md)'s token-minimization principle.
